# Runbook: перевод BTC/LTC на закрытый контур (Фаза 3)

> ## ✅ ВЫПОЛНЕНО 27.07.2026 для BTC и LTC
>
> Оба кошелька переведены в watch-only, плейнтекст-сид с сервера удалён.
> Документ оставлен как процедура — для повторного применения (новая монета,
> восстановление, другой сервер). Итоги прогона и подводные камни — в разделе
> «Журнал выполнения» внизу.

Цель — убрать приватный ключ (мастер-сид) BTC/LTC из **плейнтекстового**
`~/.bitcoinlib/database/bitcoinlib.sqlite`. После этого единственная копия сида
остаётся в шифр-вольте, а легаси-кошелёк превращается в watch-only: адреса и
баланс читаются как раньше, отправка идёт только через вольт.

Выполняется **вручную по SSH** — нужен пароль вольта, которого нет и не должно
быть у агента.

## ⛔ Шаг 0. БЛОКИРУЮЩЕЕ: починить пароль в `bot/.env`

Сейчас secure-контур **не работает**: при каждом старте бот пишет
`разлочка secure BTC не удалась: invalid_wallet_password` (14 раз за 7 дней).
Выплаты BTC/LTC идут по легаси-пути — тому самому, который Фаза 3 отключает.

**Причина найдена:** в `/root/bot/.env` переменная задана ДВАЖДЫ, разными
значениями:

| строка | длина значения | результат проверки на вольте |
|--------|----------------|------------------------------|
| 171    | 15 символов    | ✅ **открывает вольт**        |
| 172    | 13 символов    | ❌ не подходит (устаревший)   |

`load_env()` в `bot/main_bot.py` присваивает переменные по очереди, поэтому
**побеждает последняя строка** — то есть неправильная. 13 символов совпадает с
длиной пароля, скомпрометированного 25.07.

**Что сделать:**

```bash
cp /root/bot/.env /root/bot/.env.bak_$(date +%Y%m%d)   # бэкап (в .gitignore)
sed -n '171,172p' /root/bot/.env                        # убедиться глазами
sed -i '172d' /root/bot/.env                            # удалить УСТАРЕВШУЮ строку 172
grep -c '^WALLET_PAYOUT_PASSWORD=' /root/bot/.env       # должно стать 1
systemctl restart exchange-bot
journalctl -u exchange-bot -n 30 --no-pager | grep -i "secure"
```

Успех — в логе **нет** `разлочка secure BTC не удалась`.

> ⚠️ Если после удаления строка 171 сместится — сначала проверьте `grep -n`,
> удаляйте по номеру ПОСЛЕ проверки. Значение пароля никуда не выводите.

Пока шаг 0 не сделан, к шагу 3 **не переходить**: убрать легаси при нерабочем
вольте — значит остаться вообще без возможности платить BTC/LTC.

## Шаг 1. Копия шифр-бэкапа ВНЕ сервера

Вольт без копии — одна точка отказа. Файлы:

```
/root/wallet_data/backups/obsidian-btc-wallet-backup.json
/root/wallet_data/backups/obsidian-ltc-wallet-backup.json
```

Они зашифрованы паролем вольта, поэтому их можно хранить где угодно, но
**пароль хранить отдельно от них** (иначе копия = открытый ключ к деньгам).

```bash
# с локальной машины
scp root@СЕРВЕР:/root/wallet_data/backups/obsidian-*-wallet-backup.json ./
```

Проверьте, что скачанный файл читается и содержит поле `vault`.

## Шаг 2. Проверка, что вольт и бэкап сходятся

```bash
/root/bot/venv/bin/python3 /root/relay/wallet/btc_cli.py status btc
/root/bot/venv/bin/python3 /root/relay/wallet/btc_cli.py balance btc
```

`configured: true`, баланс совпадает с ожидаемым. То же для `ltc`.

## Шаг 3. Собственно harden

```bash
/root/bot/venv/bin/python3 /root/relay/wallet/btc_cli.py harden btc
# затем то же для ltc
```

Команда спросит подтверждение (`ДА`) и пароль вольта. **Все проверки идут ДО
удаления**: расшифровка вольта → расшифровка бэкапа тем же паролем → сверка,
что оба дают ОДИН сид → сверка xpub вольта с xpub легаси-кошелька. Если хоть
одна не сошлась — аборт, легаси не тронут.

Успешный вывод содержит:
```
watchOnly: true, privateKeyPresent: false, addressesMatch: true
```

## Шаг 4. Проверка после

```bash
/root/bot/venv/bin/python3 /root/relay/wallet/btc_cli.py balance btc   # баланс читается
systemctl restart exchange-bot
journalctl -u exchange-bot -n 30 --no-pager | grep -i secure           # разлочка ок
```

Затем **тестовая выплата на малую сумму** через `/worker` или реальную заявку —
убедиться, что отправка идёт через вольт и txid появляется.

## Откат

Если что-то пошло не так, легаси-кошелёк восстанавливается из сида вольта:

```bash

```

Адреса пополнения остаются прежними.

### ⚠️ Подводный камень 1: `addressesMatch: false` — это НЕ ошибка

Команда вернула `addressesMatch: false` при `watchOnly: true` и
`privateKeyPresent: false`. Разбор показал: сверка сравнивает **упорядоченные**
списки адресов, а пересозданный watch-only генерирует другой набор
**неиспользованных** ключей (change-цепочка восстанавливается иначе).

Проверено строго — списки адресов до/после сопоставлены по снимку легаси-БД:
у BTC «пропало» 6 адресов, у LTC 11. **Все они пусты и имеют 0 транзакций**
(проверено на цепи через mempool.space и litecoinspace.org). Ни один
использованный адрес не потерян, адрес со средствами на месте.

Как перепроверить самому, если увидите то же:

```bash
# адреса из снимка ДО
sqlite3 СНИМОК.sqlite "SELECT k.address FROM keys k JOIN wallets w ON k.wallet_id=w.id WHERE w.name='PayoutWallet'"
# сравнить с текущими: Wallet('PayoutWallet').addresslist()
# «пропавшие» пробить на цепи — если баланс и tx_count нулевые, всё в порядке
```

### ⚠️ Подводный камень 2: снимок легаси-БД содержит открытый сид

Снимок, который делается для отката, — это **полная копия плейнтекст-ключа**.
Оставить его на диске значит свести смысл Фазы 3 к нулю. После верификации
уничтожать:

```bash
shred -u -n 3 /root/backups/bitcoinlib_pre_harden_*.sqlite
```

Контрольная проверка, что открытых ключей на диске не осталось:

```bash
grep -acE '(zprv|Mtpv|xprv|Ltpv)[A-Za-z0-9]{20,}' /root/.bitcoinlib/database/bitcoinlib.sqlite
# ожидается 0; для валидации самого метода — тот же grep по старому снимку даст >0
```

⚠️ Не писать проверку как `if grep … | head; then` — статус берётся от `head`,
который возвращает 0 всегда, и проверка будет врать.

## Почему это важно

До Фазы 3 мастер-сид (полный контроль над средствами) лежит в plaintext в
`bitcoinlib.sqlite`. 25.07 этот файл был найден с правами **644 — читаемым всем
в системе**; права исправлены на 600, но сам плейнтекст остался. Любое чтение
файла = потеря всех BTC/LTC. Фаза 3 закрывает это окончательно.
